# JEV-9B 改动的性能回归核查（2026-10-08）

## 范围与条件

- 当前版本：`bf5add7`；改动前：`ad87cfc`。两者包含相同的俄罗斯方块代码，仅隔离后续 JEV-9B / LoRA / 分词器改动。
- 历史最佳记录对应 `bd00721`，采用保留的原始测试脚本及结果，不把历史口述数字当作同条件测量。
- 本机 M5 / 24 GB，系统 Chrome 154.0.8037.98、headless、Metal、WebGPU。各版本从隔离的只读源码快照提供页面；未切换主工作树。
- 所有权重由页面原有 file / directory input 从本地磁盘加载，禁止模型 HTTP 请求；每次 release 并关闭该次浏览器后才加载下一模型。
- LLM 使用历史的三个英语摘要输入（每段重复四次）、`max_new=128`、`do_sample=false`、`enable_thinking=false`；另测 30B 默认采样。速度按 worker token 时间戳计算，不混用总请求耗时或 SDK 的另一计时口径。
- 决策模型使用同一账单场景，测单题、三题、改变金额的新输入，以及间隔两秒的请求。分别保留关闭/打开 profiling 的结果。
- 本次完整模型性能对照是 **WebGPU**；WebGL/CPU 做了修复相关的浏览器数值和缓存验证，不能将其说成完整模型性能对照。

### 30B：历史代码本身今天也会变慢

`bd00721` 原样重跑：贪心 39.0 / 38.8 / 37.4 tok/s，随后默认采样 36.4 / 36.0 / 32.5 tok/s。当前版本首次对照的默认采样为 39.6 / 40.1 / 39.5。不能把历史 43 与今天某次 33 的差值直接归为 JEV 代码回退，也不能单凭采样选项解释整个差距。

JEV 前后都是 1061 次 decode dispatch，GPU 常驻约 12.79 GiB、峰值约 13.64 GiB；没有多出一层解码计算或一份大权重。六次生成的文本全部相同。

大模型加载与首次请求仍有明显系统状态干扰：30B 两版本加载约 56–57 秒，旧版第一条请求出现 38.6 秒 TTFT；当前版该轮从启动到释放期间，系统累计换入约 14.3 GiB、换出约 17.4 GiB。这些是全系统计数，不是按进程或按算子归因。不能据此声称已经精确分清温度、GPU 频率、分页、其他进程争用各占多少。

### 27B：保存的同一组慢轮次路径能恢复速度

没有修改 `bf5add7` 代码，复用该慢轮次保存的同版本调优配置再次加载：7.72 / 7.40 / 7.11 tok/s；休息 55 秒后 7.55 / 7.23。导入 346 条记录，加载后 `_TUNED` 与慢轮次逐项相同，三次生成文本也相同。因此不是这组算法或 JEV 后代码固定只能跑 4 tok/s。

固定 Q4_K GEMV（K=5120, N=45056）由 GPU 时间戳测得：生成前 1.108 ms、三条生成后 1.183 ms、休息后 1.174 ms。这次没有重现历史 1.06→1.72 ms 的大幅硬件执行变慢，不能把那个历史实验冒充本次慢轮次的直接测量。慢轮次的第一条请求期间另有约 491 MiB 换入、15.7 GiB 解压活动；后续两条仍慢，说明不能仅凭第一条分页解释全部波动。

## 已确认并修复的代码问题：无关模型的调优缓存被整体失效

`_kernel_build()` 原来扫描所有 WGSL 字符串。JEV 新增 `_LORA_WGSL`，把公共缓存戳从 `c958e857abcdb1ba` 改成 `26f264d2389ef26c`，尽管普通模型依赖的 shader 和数值校验未变。`use_kernel_profile()` 因此拒绝整个旧 profile，连不带 adapter 的模型也重测。

修复：

1. 公共 kernel 戳仍覆盖原有 shader、生成器和校验，排除独立的 LoRA 扩展模板。
2. LoRA 的源码、布局常量、候选与校验单独产生内容戳，进入其叶子测量键及依赖它的上层 decoder-plan 键。GGUF、非 GGUF 和 WebGPU/WebGL 的上层键都覆盖 adapter 依赖。
3. 兼容**完全匹配当前源码**的旧全量戳，保留今天已测好的公共路径；不是接受任意旧构建。公共 shader 变化仍拒绝旧 profile，旧 LoRA 路径键不会冒充新扩展的测量。
4. 没有改 shader 算术、权重位宽、后端选择、模型列表或回退规则。没有模型名分支。

## 冷加载补查与本次固化边界

- 首轮逐层同步测量：MLP 42.78 / 44.87 s；预先排空队列仅 2.24 ms。逐层同步改变了资源驻留，不能拿它验收普通请求速度。
- 整步时间戳：首次墙钟 17.51 s，GPU 算术 31.15 ms；第二次墙钟 60.14 ms，GPU 算术 21.26 ms。进程内存快照中，约 12.8 GiB 图形分配有 10.8 GiB 被换出。
- 保留有限范围的整步提交，上传、读回等显式依赖屏障仍照常提交，异常也会退出范围；正常推理的空闲提交策略不变。预热出错明确上抛，不再吞掉。
- 普通整步提交样本：预热 27.22 s，完整加载 48.60 s；第二次同步 35.83 ms；首 token 1.26 s，三次贪心 37.7 / 39.2 / 36.7 tok/s。六段输出与相同 profile 的旧结果一致。
- 不采用临时读取、专家窗口、预分配、整批转置或关闭额外运行时实验。另一个样本仍有预热 43.68 s / 完整加载 64.34 s。后观察到的训练进程于 17:47:16 启动，而该样本已于 17:46:18 结束，不能归因于那个训练进程。
- 已完成检查：主机 352 passed / 17 skipped，随后新增的两个异常回归单独通过；JS 130 passed。用户随后接受 31 秒等待并明确要求停止测试、提交当前状态，本次未继续跑模型。

这些结果没有证明任意系统内存压力下都满足 31 秒，更不是完整加载仅 31 秒。快样本、慢样本及侵入式诊断分别保留，不以某个最小值声称全局最优。冷加载原始记录另存于本地 `scratch/cold-load-2026-10-08.tgz`。
