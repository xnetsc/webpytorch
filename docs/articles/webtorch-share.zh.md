# 浏览器里跑 30B 大模型，难的不是算力

webtorch 是一套跑在浏览器里的 PyTorch 风格 SDK，底层是 WebGPU。

先看结果（下面这些都跑在浏览器里，无需额外环境准备）：

| 模型 | 体积 | 速度 |
|---|---:|---|
| Qwen3-0.6B | 0.4 GB | 每秒约 175 个 token |
| Qwen3-30B-A3B（MoE） | 13.8 GB | 每秒约 42 个 token |
| Qwen3.8-27B（混合 SSM） | 9.8 GB | 每秒约 7 个 token |
| 22 层的决策模型 | 0.7 GB | 一道题 15 毫秒左右 |

机器是 M5 MacBook，浏览器是 Chrome，下同。

---

## 一、为什么是浏览器

本地部署最烦的不是模型，是环境。CUDA 和驱动版本要对上，AMD 要看 ROCm 认不认卡，Mac 走 Metal，Windows 笔记本可能只有一块 Intel 核显，再加上 Python 版本、编译选项……很多人还没见到模型，就倒在装环境上了。

WebGPU 把这摊事甩给了浏览器厂商：写一份 WGSL，浏览器翻译成 Metal、Vulkan 或 D3D12，苹果、NVIDIA、AMD、Intel 的卡都能跑，驱动和厂商的差异是浏览器的事。

好处还有：打开网页就能用；权重存在浏览器缓存里，问什么都不出本机；算力在本机，不用为每次推理付服务器钱；没有 WebGPU 的老环境退到 WebGL，慢，但能跑。

用 Python，是因为写模型的人习惯 PyTorch。Pyodide 把 CPython 编译成 WebAssembly 跑在页面里，webtorch 在上面实现了 PyTorch 风格的接口：`Tensor`、自动求导、`nn.Linear`、`optim.Adam` 都有，`import torch` 也能直接指过来，写过 PyTorch 的基本不用改代码。

```python
import webtorch
webtorch.use_default_io()

lm = await webtorch.AutoModelForCausalLM.from_pretrained("/models/qwen3-30b-a3b.gguf")
print(lm.generate("为什么这件事让人意外？", max_new=64))
```

这段代码直接在页面里跑。

最早想在 WebGL2 上冒充 `navigator.gpu`：WGSL 翻成 GLSL，用片元着色器算，这样只认 WebGPU 的库在老浏览器上也能跑。向量加法跑通了，然后发现 WebGL2 根本没有计算着色器：片元着色器一个像素只能写一个结果，任意位置写、原子操作、共享内存、组内同步全都没有，这是规范定死的。

现在的做法是每个算子写两套，WebGPU 一套，WebGL 一套。底层用 WgPy，两套后端、Pyodide 集成、Python 同步拿 GPU 结果，这三块它都做完了。

## 二、结构和规矩

```
你的代码（PyTorch 风格）
   ↓
webtorch：张量、自动求导、nn、大模型引擎、量化、ONNX
   ↓
WgPy 数组层
   ↓
WebGPU（WGSL）／ WebGL（GLSL）
```

Python 跑在 Web Worker 里，GPU 设备在主线程。Python 同步拿 GPU 结果靠 `SharedArrayBuffer` 加 `Atomics.wait`，所以页面必须开跨源隔离（COOP/COEP 响应头）。没开隔离，`SharedArrayBuffer` 用不了，模型会一声不吭退回 CPU，慢三十倍，现在会直接报出原因。

真正决定这套东西长什么样的，是这么几套规矩：

1. **Python 只调度。** 计算、存储、拷贝、传输都在 JS 和 GPU 那边，Python 手里只有缓冲区编号。Python 和 JS 之间每跨一次都有开销。
2. **能一次办完的，不分十次。**
3. **用什么能力，先问设备。** 不同机器的显卡硬件有区别，比如 Intel、英伟达、AMD 等等。
4. **存的什么格式，就按什么格式算。** Q4_K 的权重就在着色器里按 Q4_K 解码，不偷偷转 fp16。要换精度，作为候选明着参赛，过精度关，实测赢了才用。
5. **谁快，当场比。** 同一个算子往往有好几种写法，这台设备、这种格式、这个形状下谁快，当场比一次，记下来。不设"快 5% 才换"的门槛，统计上站得住就算赢。
6. **接口按任务来，不按模型名写分支。** 模型长什么样，读它自己的配置。

## 三、踩过的坑

### 1. 慢在 Python 和 JS 之间

刚跑通训练时，一个很小的 Transformer 一步好几秒。profile 结果：一步 21 毫秒，17 毫秒花在 Python 遍历计算图、逐个下发算子上，GPU 大部分时间在等。决策模型更离谱：一次前向，Python 下发 550 个计算任务花了 36 毫秒，GPU 真正算的只有 0.7 毫秒。

WebAssembly 里 Python 每调一次 JS 都有一笔固定开销，单次不大，架不住一步成百上千次。

办法是录一次、回放多次：第一次运行时，JS 那边把这一步的所有命令原样录下来（哪个内核、绑哪些缓冲区、开多少工作组），之后只把新输入写进原来绑定的缓冲区，一次调用整段回放。结果逐位一致，快 17.8 倍。

录制回放有三个问题：

- **缓冲区编号会被回收。** 底层的缓冲区池会把释放的编号分给新的缓冲区，录下的命令按编号找缓冲区，编号被占了，回放就读到不相干的数据，结果全是 NaN。所以录制用到的缓冲区要占住，不让池子回收。
- **占住了，忘了还。** 27B 上同一个问题聊一轮慢一轮，一刷新立刻快一倍。每次生成都重录解码步，新录制占了一批缓冲区，旧录制占的那批一直没还，越积越多。现在谁录谁还，重录前先放掉上一次占的。
- **第一次录多了。** 27B 每条回复前半段都慢三倍，到第 447 个 token 突然变快。某种形状第一次运行时会注册内核，注册时顺带跑一次数值自检；第一次恰好发生在录制中，自检命令被录了进去，之后每个 token 都白跑一遍，一共多了 1728 条命令。现在加载时先不录，空跑一步，再开始录。

### 2. GPU 缺的不是带宽，是活儿

决策模型一次请求几十到几百个 token，矩阵很扁。试过的优化和结果：

- 激活函数融合进前一步，命令少了四分之一，几乎没变化；
- K/V 补齐对齐，换成单测快一倍的内核，整体反而更慢；
- 权重量化到 int8/int4，读的数据少了好几倍，速度只剩一半左右。

管用的是另一处：矩阵乘有两个内核，快的那个要求行数是 32 的倍数，行数就是 token 数，调用方控制不了，几乎每次都掉进慢内核。放开这个限制，矩阵乘快了 6 倍。

这个规模下 GPU 缺的是活儿：同一个内核、同一份权重，69 行时 234 GFLOPS，800 行时 1573。解量化本身就是计算，计算正是这里最缺的，所以量化反而变慢。量化是为了装得下（27B 不量化放不进来），不是为了快。

### 3. 解码时别让 GPU 等主机

解码时每出一个 token，主机都要等 GPU 算完、读回结果、选出下一个 token、再喂回去。15 万词表的 logits 有 600 KB，但在苹果统一内存上实测，读 4 字节和读 608 KB 一样快，只差 0.015 毫秒，根本没有搬数据，花时间的是等待本身。

做法：

- 选 token 直接在 GPU 上做；
- 位置计数、旋转位置编码要用的那几行也放 GPU 上，内核自己往前推；
- 主机读第 n 段结果时，第 n+1 段已经排进 GPU，每轮只跨一次边界。

0.6B 解码从每秒 140 左右到了 175 以上，生成的文本一个字没变。

### 4. 和 MLX 的对比

决策模型三道题，实测 MLX 原生只要 19 毫秒，WebGPU 上最初却要 100 毫秒。注意力算子合并下发、LayerNorm 顺手做残差加法、多道题首尾相接避免按最长补齐，这套优化下来，压到 44 毫秒。

剩下的差距在平台：矩阵乘在这块芯片上约 4 TFLOPS，半精度理论峰值 6.2；MLX 能到 12，走的是苹果自己的矩阵单元，WebGPU 用不了。Chrome 实验性的 subgroup matrix（要开开发者开关）实测 3.9，还是普通计算单元。

日常用的体感是 MLX 二十多毫秒，这边第一次八九十，平时五六十。这两个数的测法不一样：MLX 是连续发请求测的，这边是隔几秒问一次。苹果芯片闲一会儿就降频：GPU 闲过 200 毫秒，同样的活儿慢 2.6 倍；CPU 闲过 50 毫秒，慢三四倍。一个平时 0.77 毫秒的内核，从空闲开始连续跑，依次是 3.6、2.4、2.0、1.5、1.2、0.98 毫秒，要连续干十几二十毫秒才拉满。隔几秒问一次，每次请求都落在一块刚睡醒的芯片上。

MLX 也一样：

| | 连续发请求 | 每隔 2 秒一次 |
|---|---:|---:|
| MLX，一道题 | 7.6 ms | 35.8 ms |
| webtorch，一道题 | 15 ms | 32~38 ms |
| MLX，三道题 | 19.0 ms | 48.2 ms |
| webtorch，三道题 | 44 ms | 64~70 ms |

隔两秒问一道题，两边打平；三道题还差 1.4 倍左右，是矩阵单元的差距。

连续还是间隔、峰值还是稳态、贪心还是采样，条件不同的数字不能比。拿贪心的 110 tok/s 对采样的 84，白追了好几轮不存在的性能回退，最后发现是默认温度变了😂

### 5. 第一次慢，第二次更慢，第三次才快

录下的命令只对录制时的形状有效，而提问长度每次都不一样，24 个真实请求里有 14 种长度。原来的做法：长度向上取整到 32 的倍数，新长度第一次直接跑（顺便比出实现方案），第二次再录。所以新长度第一次慢，第二次更慢，之后才快。

回放是 JS 一条条下发的，不是一个拆不开的 GPU 命令包，所以每次回放都能按这次的实际行数，重新算每条命令开多少工作组。

现在按容量录：128、256、512 行各录一次，加载时录好。每个按行处理的内核，录制时登记一条规则：行数变了，工作组数怎么变。矩阵乘是行数除以 32 向上取整，逐元素运算是行数乘宽度除以 64，注意力按最长那段的长度、题数、头数算。回放时传入实际的行数、题数、最长长度，每条命令只开够用的工作组，不超过录制时的数量。

多出来的行里是上一次的残留数据，每个内核只拿本行算本行，注意力只读自己那段，不碍事。每次录完再用一个凑不满整块的行数回放一遍，和录制结果逐位比对，不一致加载直接报错，不把问题留到回答里。

Q8 版决策模型按真实用法跑，前两次请求从 70、78 毫秒降到 23、29 毫秒，之后再没有请求需要录制。

### 6. 测速不准

"谁快用谁"的前提是测得准，有几种容易测错的情况：

- **垃圾回收混进计时。** 一个矩阵乘选了慢 30% 的实现：快的那个平时 0.52 毫秒，有两个样本是 1.5 毫秒，各赶上一次 Python 垃圾回收加显存回收，两两对比成了 7 胜 2 负，没过显著性门槛，按规则退回默认，也就是慢的那个。现在计时期间暂停垃圾回收，回收挪到样本之间。
- **浏览器时钟不准。** `performance.now()` 被故意降了精度、加了抖动，还把主机下发和等待读回都算了进去。设备支持就用 GPU 自己的时间戳：一个样本的命令中途不提交，把每个计算通道的起止时间加起来，就是纯 GPU 时间。
- **GPU 时间戳也被调粗了。** 不开开发者开关的 Chrome，时间戳 65.5 微秒一档，2 微秒的小内核读出来不是 0 就是 65.5。测试脚本启动的 Chrome 都带着这个开关，时间戳精确到纳秒，测试环境比普通浏览器准得多，照测试环境调的参数，换到普通浏览器就失真。所以每个样本跑多少次不写死，按设备实际的时间戳精度定，凑够三十档左右；精度就是所有读数共同的那个 2 的幂次因子。
- **刚睡醒的 GPU 要热身。** 从空闲开始比，前几轮都在升频的斜坡上，两两对比的两个样本不在同一个频率。现在开赛前先跑几轮，直到某一轮不再比上一轮快才开始计时；紧跟在别的比赛后面的，GPU 本来就是热的，不用热身。
- **精度校验靠运气过了。** 半精度分块内核每 32 个乘积在半精度里累加，误差跟输入有关：27B 的一个 6144×5120 Q4_K 权重，换一组输入，误差从输出量级的 0.3% 到 1.6% 不等，门槛是 1%。加载时那组随机输入过了，重测时换一组没过。现在近似路线按权重再用两组固定的难输入查一遍（少数大值混在小值里，少数特别大的值混在普通值里），过了才让它参赛。改成单精度累加，误差能降到 0.02%~0.16%，但提速也基本没了，所以保留半精度累加，只用在查得过的权重上。
- **同一个会话里改参数对比，结论能是反的。** 在会话里改常量对比，整步快了 31%；干净重载再测，慢了 5%。现在只认一个流程：改代码、重新加载、加载模型、再测。

### 7. 显卡不一样，能力也不一样

三个模型加载时注册的 178 个内核，对照 WebGPU 规范保证的最低能力过一遍，36 个在最低配设备上跑不了：

- 12 个解码内核用了 17.4 KB 工作组共享内存，规范只保证 16 KB；
- 一个内核绑了 9 个存储缓冲区，规范只保证 8 个；
- 打包点积要求浏览器支持一个专门的 WGSL 语言特性。

M5 上这些全支持，问题永远不会暴露；换一块只有规范最低能力的显卡，加载直接失败。现在每个内核注册时都查一遍：用了哪些特性、绑几个缓冲区、要多少共享内存，对照设备报上来的能力（没报的按规范最低值算），跑不了的直接退出比赛，不等编译失败。

### 8. 不报错的错

- **着色器编译失败，不报错。** 底层建计算管线前不检查编译结果，坏的着色器被静默跳过，输出缓冲区原样不动，读回来全是 0，看着就像内核在一组全零的权重上正常跑完了。有个内核因此被禁用了很久，原因是一个字面量 `-3.4028235e38`，超出 32 位浮点的表示范围，WGSL 直接拒收。现在编译结果一律检查。
- **对话缓存复用错。** 一个开了很久的页面，模型开始复述提示词，后面跟一串乱码；同样的代码和模型，新开页面完全正常。生成过程中新内容已经写进 KV 缓存，但"缓存里存的是哪些 token"这份清单只在正常结束时更新。中途停止、报错，或者流式输出被页面中途丢下，清单停在上一轮，下一次复用的就是装着别的对话的那些行。前向是对的、输出是乱码，先清对话缓存。
- **内存涨到吓人。** 27B 生成时整台机器卡顿，9.8 GB 的模型占着 36.9 GB、七万多个缓冲区：循环引用里的垃圾没及时回收，系统只能拼命压缩、解压内存页。现在分配时按额度增量回收，阶段切换时完整回收一次。

### 9. 随时重测

设备会变，驱动会更新，机器会发热降频，测量本身也会出错，所以加了 `remeasure` 接口，随时把当前模型用到的方案重新比一遍：

- **只比当前模型真正用到的。** 加载、录制、请求里实际查过的那些，不是 SDK 支持的全部。
- **擂主制。** 在用的方案是擂主，挑战者要在两两对比里证明比它快才换；比不出差别，什么都不动。最早的版本比不出结果就退回静态默认值，没有证据就换掉了证明过的选择，还连带重录一堆命令序列。
- **组合不全排列，一次只改一处。** 解码那层的组合方案，原来是各维度全排列去比，一轮 147 个组合，只能离线跑。现在从当前方案出发，每次只改一个维度的一个取值，先过精度校验，再和当前方案在各自录好的命令序列上交替回放比速度，证明更快才采纳。30B 一次重测试了 18 个挑战者，换上 1 个，用时三十几秒。
- **随时能停，停了不白干。** 比完一项立刻生效；中途喊停，只丢正在比的那一项，比完的全保留。总时间上限默认 60 秒，到点按停止处理，没比到的空闲时接着比。每次从最久没比过的开始，进度跟设备档案一起存，不会因为总在同一个地方超时，后面的永远轮不上。
- **方案变了，用到它的录制自动重录。**
- **两套路线随时切。** 重测换下来的那套留着，正在用的那套最近三次都比另一套最近三次慢，就通过回调通知，切不切由调用方决定，两套之间随时切。再测出新路线时，丢掉的是没在用的那套。

某次遇到过重测后 0.6B 解码从每秒 175 掉到 152 的问题，即使把改过的 20 条方案全部恢复也不行，问题大概就不在方案本身。后续查到的原因：解码那层在交互模式下不真正比较，直接套一个精确的参考方案，这个方案的取 token 方式加上按上一次调用的采样设置推出来的取词模式，凑一起关掉了贪心解码的流水线，每个 token 又回读 600 KB 的 logits。

改动全撤回、问题还在，就不是改动的问题，是状态的问题。

27B 也遇到过重测后解码从每秒 7 个掉到 4 个的问题，换回原来的路线也不行。拿一个固定内核测 GPU 自己的时间：凉的时候 1.06 毫秒，重测刚结束 1.48 到 1.80 毫秒，同一个内核慢了 1.6 倍，芯片降频了。不重测、连续回复一分钟也一样，空闲一分钟就恢复，同期的换页量可以忽略。新旧两套路线在同一时段交替跑，速度都是每秒 7.92 个，一模一样。所以重测后的速度要等机器缓过来再算，判断哪套快只认同一时段交替测。

修完后，0.6B 重测前后解码速度不变。小内核改用 GPU 时钟计时后，27B 加载从 37 秒降到 31 秒，30B 从 41 秒降到 39 秒，生成内容一字不差。

## 四、几条经验

- **先找到真正卡住的地方，再动手。** 决策模型上那几个"道理上肯定有用"的优化，一半没用，一半更慢；管用的那个什么都没减少。
- **比之前先对齐条件。** 条件不同的两个数，比出来的结论经常是反的。
- **验证最终输出。** 看回答，听声音，别只看中间指标。"前向数值对得上"和"回答是对的"之间，隔着缓存复用、采样状态、录好的命令序列……
- **宁可报错，不要悄悄退回。** 能力不够就明确拿掉，编译失败就报错，测不了的写明原因。悄悄退回只会把问题藏起来。
- **平台的天花板要认。** WebGPU 用不了苹果的矩阵单元，差距测清楚就够了。第一次请求从七八十毫秒降到二十多毫秒，比死磕峰值算力有用得多。
